# `mtyx` 1.0 Stability Contract & Release Gate

`1.0` is a stability contract, not a marketing milestone. This document defines the six promises `mtyx` (`mattyx`) makes to users and script authors across the `1.x` series, and pins the verification tests that enforce each gate.

## 1. Semver on User-Facing Surfaces

Throughout `1.x`, the following three surfaces are covered by semantic versioning (no breaking changes without a major version bump):

1. **CLI Verb & Flag Surface (`mtyx <verb>`):**
   - Existing verb names (`cli::VERBS`), shorthand aliases (`ls`, `new`, `at`, `read`, `shot`, `gc`), the `mtyx agent <start|prompt|wait|read|list>` noun, and `mtyx pane worktree <create|list|remove>` remain stable.
   - Both `--flag value` and `--flag=value` forms are accepted in any position before `--`.
   - With `--json`, errors always emit the structured `{"ok":false,"error":{"code":...,"message":...}}` envelope on stdout and preserve documented exit codes (`0` success, `1` server/operation error, `2` bad flags/usage, `3` socket connect failure).
2. **Control Socket Wire Protocol (`PROTOCOL_VERSION = 8+`):**
   - `PROTOCOL_VERSION` only increments on breaking framing/handshake changes; new commands, optional request fields, additional reply fields, and new `subscribe` event kinds are strictly additive.
   - Feature negotiation uses `identify`'s `capabilities` map (e.g. `capabilities["input-ack"] == true`) rather than raw version arithmetic.
   - Reply shapes for read-only and agent-factory commands are pinned by golden tests in [`mux/crates/mux-core/tests/wire_contract.rs`](../crates/mux-core/tests/wire_contract.rs), and `protocol_compat_matrix_in_docs_matches_protocol_version` verifies that [`mux/docs/protocol.md`](./protocol.md) never drifts from `mux_core::PROTOCOL_VERSION`.
3. **Configuration Schema (`mux.json` / `mux.toml`):**
   - Every documented key in [`mux/docs/configuration.md`](./configuration.md) is optional.
   - `schema_version` (optional integer, currently `1`) is accepted in `mux.json` and `mux.toml`. Accepted values: absent (every `0.x` config) or `1`; any other value makes the config invalid with an error naming the supported version (`unsupported schema_version N: this mtyx supports schema_version 1 only; ...`), pinned by `config::tests::schema_version_accepts_absent_or_one_and_rejects_other_values`. Policy: a higher version means the file was written by a newer `mtyx`, so it must fail loudly rather than load under 1.x semantics; schema changes within `1.x` are additive only. See [`configuration.md`](./configuration.md) §Schema version.

## 2. Config & State Migration Guarantees

Any configuration file (`mux.json` / `mux.toml`), session snapshot (`$XDG_STATE_HOME/mattyx/sessions/<session>.json`), or environment variable setup from any `0.x` release continues to work on `1.x`:

- **Legacy `CMUX_*` Environment & Runtime Compatibility:**
  - If `MTYX_MUX_SOCKET`, `MTYX_MUX_CONFIG`, `MTYX_MUX_WORKSPACE`, `MTYX_MUX_SURFACE`, or `MTYX_MUX_SESSION` is unset and its `CMUX_*` counterpart is set, `mtyx` copies the value into `MTYX_*` at startup (`honor_legacy_env`).
  - Session discovery and socket resolution check the canonical `mtyx-<uid>` runtime directory first and transparently fall back to a live `cmux-<uid>` directory.
- **Non-Destructive Corrupt Snapshot Recovery (Issue #95):**
  - If a session snapshot file is truncated or unparseable on startup, `SessionSnapshot::load` never deletes or overwrites it in place — it renames the file aside into `$XDG_STATE_HOME/mattyx/session-backups/<session>.<unix-ts>.json` (retaining the 5 newest backups per session at mode `0600`) before starting fresh.
- **Non-Destructive Hook & Config Merging:**
  - All 7 agent hook installers (`claude`, `codex`, `antigravity`, `pi`, `opencode`, `grok`, `aider`) preserve foreign keys and existing user hooks, and propagate JSON/TOML parse errors rather than clobbering a malformed user file with defaults.
- **Test-Pinned Historical Fixtures:**
  - `config::tests::historical_0x_release_config_fixtures_migrate_cleanly` pins `v0.10`, `v0.17`, `v0.22`, and `v0.27` config fixtures, plus any per-tag fixtures extracted into `mux/crates/mux-tui/tests/fixtures/`.
  - `persist::tests::historical_0x_session_snapshots_load_and_migrate_cleanly` pins `v0.5` and `v0.17` session snapshot fixtures, plus any per-tag fixtures extracted into `mux/crates/mux-core/tests/fixtures/`.
  - **Coverage caveat:** the inline fixtures cover representative schema *eras*, not every shipped minor (27 distinct `0.x` minors / 35 tags exist). `scripts/extract-migration-fixtures.sh` scripts the per-tag extraction (`git tag -l 'v0.*'`), and the fixture tests loop over anything it drops into the fixtures directories — but running it across all tags is deferred operator work, recorded in fix-notes.

## 3. Upgrade-in-Place & Rollback

`mtyx update` (Issue #133) is the blessed in-place upgrade mechanism for standalone binary installs:

1. Queries the latest GitHub release tag and compares semver against `mux_core::VERSION`.
2. Downloads `<asset>` and `<asset>.sha256` for the host `(OS, ARCH)` (`linux-x86_64`, `linux-aarch64`, `macos-aarch64`, `macos-x86_64`, `windows-x86_64.exe`).
3. Verifies the binary's SHA-256 digest in pure Rust (`self_update::sha256_hex`) against the `.sha256` sidecar before touching the target path.
4. Stages the binary to `.mtyx-update-<pid>-<nanos>.tmp` in the target directory, sets mode `0755`, and executes `<staged> --version` to verify the binary runs on this host and reports the expected release version.
5. Atomically renames `<staged>` over `<target>` on Unix (or performs the two-step `<target>` → `<target>.old` backup swap on Windows).

### Rollback Procedure

- **Windows:** If a swap fails mid-flight, `swap_with_old_backup` automatically rolls `<target>.old` back to `<target>`. Before the next `mtyx update` cleans up `mtyx.exe.old`, you can also manually restore `move /Y mtyx.exe.old mtyx.exe`.
- **Unix / Any Platform (Pinning a Previous Release):**
  Re-run `scripts/install.sh --version v<previous>` (or download the previous tag's asset + `.sha256` sidecar from `https://github.com/mathewclarkau/mattyx/releases/tag/v<previous>`). **Merge ordering:** `scripts/install.sh` is added by PR #151 — this gate doc assumes #151 lands first (same chain); until it merges, use the releases-page download in this bullet.
  ```bash
  curl -fsSL https://raw.githubusercontent.com/mathewclarkau/mattyx/v0.27.0/scripts/install.sh \
    | bash -s -- --version v0.27.0
  ```
- **Running Sessions Survive Binary Upgrades:**
  Because `mtyx` replaces the on-disk executable via `rename(2)` (not overwriting the mapped inode in place), existing running `mtyx` daemons continue serving unaffected until you choose to restart them.

## 4. No-Leak Promise (Process & Socket Hygiene)

`1.0` guarantees that `mtyx` does not leak orphan daemons, socket-watchdogs, or stale `.sock`/`.pid` pairs:

1. **Parent-Death Socket Watchdog:** Every session daemon spawns a lightweight `socket-watchdog` child that monitors the daemon PID and unlinks the `.sock`/`.pid` pair within 200ms if the daemon is killed via `SIGKILL`.
2. **Three-Point Stale Session GC (Issues #136, #137, #138):**
   - **Daemon Startup Sweep:** `sweep_stale_sessions` reaps dead `.sock`/`.pid` pairs before binding a new session.
   - **Explicit Verb:** `mtyx kill-stale` (alias `mtyx gc`, with `--dry-run` preview) sweeps dead pairs on demand.
   - **Lazy Enumerate GC:** `mtyx list-sessions` and the TUI session picker (`Ctrl-b S`) reap stale pairs automatically on enumeration, using a double-signal check (dead PID + refused socket connection + pre-unlink re-verification).
3. **Suite-Level Leak Guard (Issue #139):**
   - [`mux/crates/mux-tui/tests/no_leaked_daemons.rs`](../crates/mux-tui/tests/no_leaked_daemons.rs) scans `/proc` for any live non-zombie process carrying the test run's `MTYX_TEST_RUN=<tag>` environment marker and fails the build if a single `mtyx` daemon or watchdog outlives the test suite.

## 5. Windows Out-of-Beta Criteria

Windows support (`mtyx-windows-x86_64.exe`) uses native Win32 ConPTY (`portable-pty`), AF_UNIX sockets (`uds_windows`), and Win32 file locking (`LockFileEx`/`UnlockFileEx`):

- **CI Gate:** `.github/workflows/pr-build.yml` and `.github/workflows/release.yml` build and test `windows-latest` (`x86_64-pc-windows-msvc`) alongside Linux (`x86_64`, `aarch64`) and macOS (`aarch64`).
- **Graduation Streak Criterion:** Windows drops the "beta" label once `windows-latest` maintains 10 consecutive green runs across `pr-build.yml` and `release.yml` with zero open Windows-specific P1/P2 issues.
- **Current Status (maintained in this document):** Windows streak: 0/10 (as of this PR) — the criterion is not yet met, so gate 5 remains unchecked above; update this line with each `windows-latest` CI result.
- **Explicit Out-of-Scope Boundaries (Documented, Not Bugs):**
  - Inbound SSH daemon hosting (`mtyxd-remote` and `mtyx --machine <label>` target POSIX SSH hosts only).
  - `/proc`-based ambient process-tree inspection (Windows uses screen-marker detection and explicit/hook agent reports).

## 6. Security Posture

`mtyx` enforces five non-negotiable security invariants across the codebase:

1. **Symlink Check Before Write:**
   - Every file writer that mutates user config, layout exports, screenshots, or the `mtyx` binary itself (`self_update.rs`, `install.sh`, `cli.rs` `screenshot`/`layout-export`, and all 7 hook installers) checks `fs::symlink_metadata` (or `[ -L ... ]`) and refuses to overwrite a symlink target. A `~/.local/bin/mtyx` symlink pointing into a source checkout will never clobber the checkout target. (`scripts/install.sh` is added by PR #151; this gate doc assumes #151 lands first — see the merge-ordering note in §3.)
2. **SHA-256-Verified Binary Updates & Installs:**
   - Both `mtyx update` and `scripts/install.sh` require a matching 64-hex-character SHA-256 digest from the `<asset>.sha256` release sidecar and a matching `<staged> --version` execution check before swapping the binary into place. Release publication in `.github/workflows/release.yml` is gated on `scripts/sha256.sh verify dist`. (`scripts/install.sh` is added by PR #151; this gate doc assumes #151 lands first — see the merge-ordering note in §3.)
3. **Argv-Only Subprocess Execution (No Shell Interpolation):**
   - Subprocesses (`Command::new` in Rust, `execFile` in generated TypeScript hooks for Pi/OpenCode) pass argument arrays directly to the OS kernel. Environment variable values and user prompts are never string-interpolated into `sh -c`.
   - When dispatching text into an interactive shell pane via `mtyx send --shell <fish|bash|zsh|sh|nu|auto>`, shell-aware sanitisation (Issue #35) prefixes a buffer-reset newline before metacharacter-leading input (`$`, `!`, quotes, brackets, `~`, `#`) or unclosed quotes.
4. **Restricted Runtime & State Permissions (`0700` / `0600`):**
   - Runtime socket directories (`$XDG_RUNTIME_DIR/mtyx-<uid>`), session snapshot directories (`$XDG_STATE_HOME/mattyx/sessions`), backup directories (`session-backups`), and `machines.json` are restricted to owner-only access (`0700` for directories, `0600` for files; Issue #87).
5. **Zero Telemetry:**
   - `mtyx` collects no telemetry, analytics, or crash reports. The only outbound network request the binary ever makes is the GitHub Releases API check (`https://api.github.com/repos/mathewclarkau/mattyx/releases/latest`) during `mtyx update` or the once-per-24h TUI startup update check — which can be disabled completely via `"update_check": false` in `mux.json` / `mux.toml` or `MTYX_DISABLE_UPDATE_CHECK=1` in the environment.
